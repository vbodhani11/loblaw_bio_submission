# Loblaw Bio Immune Cell Trial Analysis

Python + SQLite pipeline and interactive Streamlit dashboard for the immune-cell clinical-trial assignment. The project loads `cell-count.csv`, calculates per-sample immune-cell relative frequencies, compares miraclib responders vs non-responders, and queries the requested baseline subsets.

## Dashboard

- Local dashboard: [http://localhost:8501](http://localhost:8501)
- Live Dashboard: [https://loblaw-bio-dashboard.streamlit.app/](https://loblaw-bio-dashboard.streamlit.app/)
- GitHub Codespaces: run `make dashboard`, then open forwarded port **8501** from the **Ports** tab.

## Quick start (GitHub Codespaces or local)

Use Python 3.11+ (the included devcontainer uses Python 3.12).

```bash
make setup
make pipeline
make dashboard
```

The grader-required Make targets are implemented exactly as requested:

- `make setup` — installs dependencies from `requirements.txt`.
- `make pipeline` — creates the SQLite database and runs Parts 2–4 end-to-end without manual intervention.
- `make dashboard` — starts the Streamlit dashboard on port 8501.

You can also run the mandatory loader directly:

```bash
python load_data.py
```

This creates `clinical_trial.db` in the repository root. `load_data.py` requires no command-line arguments and is not module-only code.

### Input data

Place the assignment file in the repository root with this exact name:

```text
cell-count.csv
```

If it is missing, `load_data.py` attempts to download the file automatically from the Google Drive link supplied in the assignment. If Google blocks automated downloading, download the CSV manually and place it in the repository root.

## Part 1 — relational database schema

The source CSV is wide and repeats subject-level metadata on every longitudinal sample. The database normalizes those concepts into five relational tables.

### `projects`

| column | type | role |
|---|---|---|
| `project_id` | TEXT | primary key |

### `subjects`

| column | type | role |
|---|---|---|
| `project_id` | TEXT | FK → projects |
| `subject_id` | TEXT | subject identifier |
| `condition` | TEXT | melanoma/carcinoma/etc. |
| `age` | INTEGER | subject age |
| `sex` | TEXT | M/F |
| `treatment` | TEXT | treatment assignment |
| `response` | TEXT | yes/no/NULL |

Primary key: `(project_id, subject_id)`.

### `samples`

| column | type | role |
|---|---|---|
| `sample_id` | TEXT | primary key |
| `project_id` | TEXT | subject FK component |
| `subject_id` | TEXT | subject FK component |
| `sample_type` | TEXT | e.g. PBMC |
| `time_from_treatment_start` | INTEGER | sample timepoint |

Composite foreign key `(project_id, subject_id)` references `subjects`.

### `cell_populations`

| column | type | role |
|---|---|---|
| `population_id` | INTEGER | primary key |
| `name` | TEXT | unique population name |

### `cell_counts`

| column | type | role |
|---|---|---|
| `sample_id` | TEXT | FK → samples |
| `population_id` | INTEGER | FK → cell_populations |
| `count` | INTEGER | non-negative raw cell count |

Primary key: `(sample_id, population_id)`.

### Why this schema?

1. **Avoids duplicated subject metadata.** Age, sex, condition, treatment, and response are stored once per subject instead of repeated for every sample and cell population.
2. **Models longitudinal biology naturally.** One subject can have many samples/timepoints.
3. **Keeps cell measurements in long format.** Adding another cell population does not require an `ALTER TABLE`; insert one lookup row and new measurements instead.
4. **Supports multi-project scale.** Project is a first-class key and the subject key is project-aware.
5. **Supports analytics efficiently.** Indexes cover the common trial filters (`condition`, `treatment`, `response`, `sex`, `sample_type`, and time).
6. **Easy path beyond SQLite.** The same normalized design can move to PostgreSQL for concurrency/scale. For very large analytical workloads, long-form measurements can also be exported to Parquet/warehouse storage while preserving relational metadata.

The loader also creates a view named `sample_cell_frequencies`, which exposes the exact Part 2 shape while keeping raw normalized tables underneath.

## Part 2 — relative frequencies

For every sample:

```text
total_count = b_cell + cd8_t_cell + cd4_t_cell + nk_cell + monocyte
percentage  = 100 * population_count / total_count
```

The generated table contains exactly:

```text
sample, total_count, population, count, percentage
```

Output: `outputs/part2_frequency_table.csv`.

## Part 3 — responder vs non-responder statistics

Primary cohort filters:

- condition = melanoma
- treatment = miraclib
- sample type = PBMC only
- response ∈ {yes, no}
- all available timepoints (the assignment does not restrict Part 3 to baseline)

For each immune population, the program performs a **two-sided Mann–Whitney U test** on relative frequencies. This is a robust non-parametric comparison and does not require normally distributed percentages.

Because five populations are tested, the program also applies **Benjamini–Hochberg false-discovery-rate (FDR) correction**. `part3_stats.csv` reports:

- responder/non-responder sample counts
- group medians
- median difference in percentage points
- Mann–Whitney U statistic
- raw p-value
- BH-adjusted p-value
- rank-biserial effect size
- significance using both nominal p < 0.05 and FDR < 0.05

The main conclusion uses **FDR < 0.05** to avoid overstating a chance finding across the five simultaneous tests. The dashboard displays the boxplots and statistical table together.

### Statistical caveat

The primary analysis follows the assignment literally at the **sample** level. Longitudinal samples from the same subject are therefore treated as separate observations. In a production clinical analysis, I would additionally use a subject-level aggregation or a repeated-measures/mixed-effects model to account for within-subject correlation.

## Part 4 — subset queries

### Baseline subset

The program identifies melanoma samples that are:

- PBMC
- treated with miraclib
- `time_from_treatment_start = 0`

It then reports:

1. number of samples by project
2. number of unique subjects by response
3. number of unique subjects by sex

### Required B-cell question

The final question has a deliberately broader scope than the baseline subset above:

> Considering melanoma males of **all sample and treatment types**, what is the average number of B cells for responders at time = 0?

The SQL therefore **does not filter sample type or treatment**. On the provided assignment dataset, the expected value is:

```text
10206.15
```

This is the mean raw B-cell count, rounded to two decimals.

## Quintazide / AI-model note

The assignment text explicitly says to **mention quintazide**. This implementation mentions it without fabricating data: no analytical conclusion is created for quintazide unless it is actually present in the input dataset. The requested Parts 1–4 do not require an AI/ML predictive model; the statistical responder comparison is intentionally kept separate from any future prediction model.

If a predictive model were added later, a reasonable next step would be a subject-aware logistic-regression baseline followed by cross-validated tree-based models using the five cell-frequency features, with strict train/test separation by subject.

## Design choices

- **`load_data.py` has one responsibility:** validate input, initialize the schema, and load rows.
- **`analysis.py` is reusable:** the dashboard imports the same query/statistical functions used by the batch pipeline, preventing duplicated logic.
- **The dashboard queries the SQLite database:** it reflects the data produced by the pipeline rather than relying on manually edited output files.
- **Outputs are deterministic:** rerunning `make pipeline` recreates the database and overwrites generated analysis files from scratch.
